## H1. 单轮输出 8192 触顶：整轮作废、无入口（报告）

报告对象是 0.3.3，但 0.3.4 代码未变，问题仍成立。

**已确认事实（当前代码）**
- `ui/shell-api/.../SettingsStore.kt:525` `DEFAULT_MAX_TOKENS = 8_192`；
  同文件 40 行注释：**「2026-11-09：用户要求删掉『最大输出 tokens』设置；请求固定用 DEFAULT_MAX_TOKENS」**
  → 这是**产品决定**，不是漏接线，报告把它当「接线遗漏」不准确。
- `SettingsStore.setMaxTokens()` 存在（`_maxTokens` 仍可写），但 `ModelConfigScreen` 没有入口；
  当前「模型与参数配置」只有上下文窗口/温度/思考强度等。
- 截断处理（`TurnEngine.kt:656-704`）：
  - 已生成的 assistant 文本与 reasoning **已经落盘**（`appendAssistantMessage`），不是全丢；
  - 截断在 `tool_use` 上时：工具**一次都不执行**（正确，参数可能不完整），每条调用补一条
    `TRUNCATED_TOOL_RESULT` error 结果保持配对，然后 `ui.setError("达到 max_tokens 上限，输出被截断（工具调用未执行）")`、
    `turn/end error` 收口；
  - 没有「继续生成」，没有把待发送队列对齐提示（插件回合路径有「待发送消息已保留」文案，
    见 `AppViewModel.kt:4580` 附近）。
- 报告证据可信：会话日志、请求头 `maxTokens:8192`、字节码常量、服务端 20k 输出实测。

**修复方案（2026-11-16 用户拍板，见 §拍板记录）**
> 拍板：**不恢复设置项、不上调默认值**（尊重 2026-11-09「删掉该项」的决定）；
> 只做「继续生成」+ 可行动文案 + 队列提示对齐。以下 1、2 标记为**不做**，保留作背景。

1. ~~入口：在「模型与参数配置」加「单轮输出上限 tokens」行~~ **（不做，用户拍板保持隐藏）**
2. ~~默认值上调到 16,384 / 32,768~~ **（不做，保持 8_192）**
3. **截断续写**：回合以 `MAX_TOKENS` 结束时，在聊天页给一个**「继续生成」**操作（不是自动重发）：
   - 点击后以用户消息「上一条回复被截断，请从中断处继续；如果要写文件，请分几段写」发起新一轮；
   - 只对「截断在 tool_use 上」和「纯文本截断」两种情况显示，`ERROR`/用户停止不显示；
   - 状态要**可恢复**：优先落成一条会话事件（或聊天状态里带 sessionId 的字段），冷启/切会话后仍在，
     不能只靠 `rememberSaveable`；「继续生成」点一次消费一次（防连点重发）。
4. **文案**：改成可行动版本（不引导去改设置，因为入口已隐藏），例如
   「本轮输出达到上限（8192 tokens），文件未写入。可以：① 让我分几段写；② 直接点「继续生成」；③ 重发一次并说明分段。」
5. **对齐插件路径**：普通会话也提示「待发送消息已保留」（队列本来就持久化，只是没文案）。
6. **源头减少触发**（低优先级）：`write` / `edit` 工具描述里写明「单次不超过 N 行，超出请分段」。

**验收**
- `maxTokens` 保持 8192、让它写大文件 → 截断后出现「继续生成」，点击后新回合从中断处继续，文件最终写出；
- 连续点两次「继续生成」只发一轮（按钮已消费）；
- 冷启/切会话回来后「继续生成」状态正确（该在的在、不该在的不在）；
- 纯文本截断（不触发工具）也有「继续生成」，且不误报；
- `turn/end` 仍是 error（语义不变），但 UI 可自救；插件回合路径文案不回归；
- 设置页**不出现**「单轮输出上限」（回归项，确认没被顺手加回来）。

## H2. 悬浮球点开再关闭后跑到「悬浮窗中心」

**已确认根因**（`app/.../device/floating/FloatingWindowManager.kt:502-518`，`switchMode`）：

```kotlin
FloatingMode.BALL, FloatingMode.VOICE_BALL -> {
    ...
    val (nx, ny) = when (oldMode) {
        FULLSCREEN, SCREEN_OCR -> (screenW - ball) to (screenH - ball) / 2
        RESULT_DISPLAY -> state.lastBallPositionX to state.lastBallPositionY
        else -> {  // ← WINDOW 走这里
            val sw = ...
            val sh = ...
            (params.x + sw / 2 - ball / 2) to (params.y + sh / 2 - ball / 2)  // ← 球放到「窗中心」
        }
    }
```

即：从 **WINDOW 关回 BALL** 时，位置算成了「窗口矩形的中心」，而不是打开窗口前球的位置。
`state.lastBallPositionX/Y` 已经在 BALL→WINDOW 时保存（472-476 行），只是回程没用。

**修复**
- WINDOW → BALL：直接用 `state.lastBallPositionX/Y`（并 clamp 到当前屏幕）；
  仅当从未记录（老数据/首次）才回退到窗中心。
- FULLSCREEN/SCREEN_OCR → BALL：同样优先回 `lastBallPosition`（现在固定右下角），
  没有记录再退回 (screenW-ball, (screenH-ball)/2)。
- 顺手：`state.saveState()` 已有 lastBall 字段，确认冷启后也能恢复。
- 单测（JVM 可测的部分）：把「回程位置选择」抽纯函数 `ballTargetOnReturn(oldMode, params, lastBall, screen)`，
  覆盖 WINDOW/FULLSCREEN/RESULT/首次 四个分支。

**验收**：球拖到左上角 → 点开窗 → 关闭 → 球回到左上角原处（不是屏幕/窗中心）；
拖到右下 → 同上；冷启后球位置保持；窗口本身位置不被回程改动。

## H3. 设置页按手机返回键回不到聊天

**已确认根因**（`NativeShellRoot.kt` 的 `openSub`，124-135 行）：

```kotlin
val openSub: (String) -> Unit = { id ->
    ...
    backPage = BuiltinPageIds.Settings   // ← 不管从哪进，都记「返回设置」
    backSub = null
    screenName = BuiltinPageIds.Settings
    subScreenName = id
}
```

从**聊天页**直接进二级页时（最主要路径：输入条上方的模型芯片 →「模型配置」，
`NativePageDispatch.kt:192` `onOpenModelSettings = { nav.openSub(ModelConfig) }`），
路由变成 `page=Settings, sub=ModelConfig`、`backPage=Settings`：

1. 按返回 → `closeSub()` → 回到 **Settings 首页**（用户以为该回聊天）；
2. 再按返回 → `backFromPage()` → `screenName = backPage = Settings` → **原地不动**。

所以用户看到的就是「设置页里返回键没用」。从抽屉进设置（`goFromDrawer`，backPage=抽屉来路）
不受影响，从设置进二级页（backPage=Settings）也正确——**只有「聊天直进二级页」这条路径错**。

**修复**
- `openSub` 记录真实来路：`fromChat = screenName == null`；
  - 从聊天进：`backPage = null`、`backSub = null`（返回直接回聊天，不经过设置首页）；
  - 从设置进：`backPage = Settings`（行为不变）。
- `screenName` 仍设为 Settings（渲染子页需要），只改返回目标；
  `closeSub`/`backFromPage` 不用改。
- 逐路径验收（真机 + `DshPage` 日志）：

| 路径 | 期望 |
|---|---|
| 聊天→模型芯片→模型配置→返回 | 回聊天（不是设置） |
| 聊天→模型配置→返回→再按返回 | 第二次交给系统（不原地卡住） |
| 设置→显示与行为→返回 | 回设置首页 |
| 设置→返回 | 回聊天 |
| 抽屉→设置→返回 | 回抽屉来路（聊天/设置，0.3.4 语义不变） |
| 设置→模型配置→返回 | 回设置首页 |

**风险**：`openSub` 也被设置页的各行使用，改动只影响 `screenName == null` 的分支，回归面小；
但要检查 `AnimatedContent` 的层级动画方向（chat 0 → Settings+sub 2 → 返回 0）是否正常。

## H4. 设置里进二级页面「非常卡顿」（用户猜是动画）

**未确认，需要先量化**（本条只给假设与测量方法，不直接下结论）。

现状：所有页面/二级页切换共用 `NativeShellRoot.kt:367-388` 的 `AnimatedContent`：

```kotlin
targetState = NavRoute(screenName, subScreenName),
transitionSpec = {
    slideInHorizontally(tween(260)) { dir * it / 5 } + fadeIn(tween(200))
    togetherWith slideOutHorizontally(tween(260)) { -dir * it / 5 } + fadeOut(tween(160))
    using SizeTransform(clip = false)
}
```

可疑点（按可能性）：
1. **整屏双份组合 + 淡入淡出**：切换时旧页与新页同时存在，两个全屏 alpha 层 + 260ms 滑动；
   设置首页是一整列 `verticalScroll`，低端机上首帧组合成本叠加。
2. **`SizeTransform(clip = false)`**：容器尺寸动画会持续 measure/layout 两棵子树（即使尺寸相同也走布局路径）。
3. **二级页首帧自身重**：`PrivacyScreen` 进页即 `measure()`（已放 IO，但会触发状态刷新重绘）、
   `AssistantScreen`/`SkillsScreen`/`PermissionsScreen` 首帧读状态多。若只有个别页卡，属于这一类。
4. 设备/系统因素：vivo Android 16、debug 包、Compose debug 模式本身慢；需要基线对比（聊天↔设置是否也卡）。

**先量化的方法**（按顺序）
1. `adb shell dumpsys gfxinfo xin.dshaa.nativeapp reset` → 进二级页 → `... framestats`，
   统计 >16.7ms 的帧数与最大帧；同时 `adb logcat -s Choreographer` 看 `Skipped N frames`。
2. 对比三条路径：聊天→设置、设置→二级页、二级页→设置。若只有「设置→二级页」卡，偏动画；
   若所有进入都卡，偏组合/首帧。
3. 临时在 `NativePageDispatch` 加 `SideEffect` 计数 + `DshPage` 打点（debug only），
   看是哪一页/哪一次重组导致的。
4. 基线：把 transition 临时改成瞬时（`EnterTransition.None togetherWith ExitTransition.None`）复测，
   确认动画占比。

**候选修复（按代价从小到大）**
- **A（推荐先试）**：二级页切换不再整屏滑入+淡入，改成
  「新页 160ms 淡入 + 轻微位移（1/8 屏）」、旧页不动画；去掉 `SizeTransform`。
- **B**：设置 ↔ 二级页完全瞬时切换（或只在新页做 120ms 淡入），其它导航保留动画。
- **C**：把 `AnimatedContent` 换成 `Crossfade`（单层 alpha，仍双组合但无位移/尺寸动画）。
- **D**：给「页面动画」加开关（低端机/无障碍），关掉即瞬时。
- **E**：若量化发现是个别页首帧重，单独把该页初始化移到 `LaunchedEffect` + IO，并加骨架/占位。

**验收**：同一设备、同一路径，`gfxinfo` 的 janky 帧比例与最大帧较基线明显下降（目标：90% 帧 <16.7ms，
主观无停顿）；聊天↔设置、抽屉、返回动画不回归；设置页滚动位置保持（`settingsScroll`）行为不变。

**首轮量化（2026-11-16 第五棒，vivo PEMM00 / debug 包）**
- 设置→显示与行为：16 帧，janky 10（**62.5%**），50th 38ms，90th 150ms；Slow UI 6、Slow draw 7。
- 显示与行为→设置：19 帧，janky 7（**36.8%**），50th 34ms，90th 200ms；Slow UI 4、Slow draw 5。
- 两条路径都明显超预算，不是个别页首帧；聊天→设置基线本次未取到，待补。
- 下一步按候选 **A** 改：二级页切换改「新页 160ms 淡入 + 1/8 屏轻位移，旧页不动画」、去掉
  `SizeTransform`；改完同路径复测，并补聊天↔设置/抽屉路径回归。证据 `docs/035-4-evidence/`（未跟踪）。

## 第二批追加反馈（2026-11-16 21:2x）

### H5. 发系统通知：授权不生效（「本版还没实现」）

**现状核对**
- `PluginPermissions.kt:130` 直接把 `notify` 描述成「发系统通知（本版还没实现，授权也不会生效）」——
  用户看到的就是这句。
- 实际代码其实**有一半**：
  - `app/.../data/PluginNotifier.kt`：会创建 `dsh_plugin_notify` 渠道并 `NotificationManager.notify(...)`；
  - 但 Android 13+ 的 `POST_NOTIFICATIONS` **没有任何请求入口**（全仓库只有 `PluginNotifier` 里一处
    `checkSelfPermission`，没 grant 就静默 return）→ 用户感觉「授权也不生效」；
  - 插件 `notify` 权限**没有被校验**：`PluginToolRuntime.kt:232` 收到 `plugin.notify` 直接调 `notifier(...)`，
    没有看 manifest 授权表；`CapabilityHost` 的内置 `notify` 只是 **Toast**，不写通知栏
    （它的 description 也这么写）。
- 结论：不是「没实现」，是**三处没接线**：系统运行时权限、插件权限门、内置 capability 仍是 Toast。

**方案**
1. **权限门**：`plugin.notify` / `agent.notify` 在 Kotlin 侧检查该插件是否被授予 `notify`；
   未授权返回结构化错误（`{"ok":false,"code":"PERMISSION_DENIED","message":"缺少 notify 权限"}`），
   不再静默成功/静默丢弃；插件页权限列表里的描述改成真实行为。
2. **系统权限**：Android 13+ 在「用户给插件勾选 notify」时请求 `POST_NOTIFICATIONS`
   （`ActivityResultContracts.RequestPermission`），拒绝则回显「系统通知权限未开」并给「去系统设置」入口；
   通知渠道复用 `dsh_plugin_notify`，IMPORTANCE_DEFAULT，可按插件分渠道（可选）。
3. **内置 capability**：`notify` 从 Toast 改为真实系统通知（同一条 `PluginNotifier` 路径，同样过权限门）；
   保留 Toast 作为 `notify.toast` 单独能力，避免语义混淆。
4. **点击行为**（拍板）：只做「打开 App 落地聊天」；跳转会话/插件页作为后续增强，不在本轮。
5. **测试**：JVM 测权限门与文案；真机 Android 13 测「未授权→拒绝且报错」「授权→通知出现」
   「关系统权限→提示去设置」；冷启后授权状态保持。

### H6. 复制 AI 消息时选区只能选一段（往下拖不动）

**已确认根因**（`ui/design/.../component/Markdown.kt`）
- `MarkdownText` 把文本按块渲染（Paragraph/Heading/Bullets/Quote/Code/Table），
  但 **每个 `InlineText` 各自包了一层 `SelectionContainer`**（267 行），代码块（241 行）也各一层。
- Compose 的选区以**最内层 SelectionContainer** 为边界：一段一个容器 → 只能选一段，
  拖到下一段就"拖不动"。用户看到的正是这个。
- 整条消息的「复制」入口是三条杠菜单（`copyMessage`），与手动选区是两条路；这次只修选区。

**方案**
1. 把 `SelectionContainer` **上提一层**：`MarkdownText` 的整列 blocks 外套一个 `SelectionContainer`；
   删掉 `InlineText` / `CodeBlock` 内部的 SelectionContainer（嵌套时最内层优先生效，必须删）。
2. 表格（`TableBlock` 的多个 `Text`）保持在外层容器内，单元格之间可连续选；如果实测跨行选区怪异，
   再给表格单独容器（可接受）。
3. 消息级（LazyColumn item）之外不跨消息选择——不追求跨消息多选，避免和滚动/Lazy 复用打架。
4. 验收：一条含 3 段+列表+代码的回复，从第一段拖到最后一段能一次选完并复制；
   代码块内选择正常；长按不误触消息菜单；表格/引用/标题都覆盖。

### H7. root：设备无 root 无法实测，参考 Operit 实现

**现状核对**
- 宿主的 shell 身份其实**已经有 root 通道**：`support/.../DeviceShell.kt`
  - `hasRoot()`：`su -c id` 输出 `uid=0` 视为可用（3 秒超时，结果缓存）；
  - `ShellIdentity.ROOT` → `su -c`；`SHELL` 优先 Shizuku、退 root；`DEFAULT` 优先 root、退 Shizuku、最后 App `sh`；
  - Shizuku 依赖（api/provider/aidl 13.1.5）与清单权限都已接好。
- 缺的是**能力层与可见性**：
  - `CapabilityHost` 的内置能力只有 notify/clipboard/share，**没有 root/shell 能力提供方**；
    插件声明 `root`/`adb-shell` 能力时无人提供 → 只能「不可用」；
  - 没有「当前 shell 身份（root/Shizuku/App）」的界面与诊断，失败时静默退化到 App `sh`，
    用户不知道为什么命令失败；
  - `su` 只试了 `su -c` 一种写法，Magisk/KernelSU/SuperSU 的变体（`su 0`、`su -0`）未覆盖。
- 开源参考（用户点名 Operit）：
  - [AAswordman/Operit](https://github.com/AAswordman/Operit)：三档权限模型
    无障碍 / Shizuku(ADB) / Root，root 还用于虚拟屏等多显示器场景；
    [README 说明](https://raw.githubusercontent.com/yang-yang9/Operit-y/refs/heads/main/README(E).md#1)
    也明确「无 root 可用无障碍/Shizuku，root 只用于虚拟屏等额外能力」。
  - 可参考的通用做法：libsu（topjohnwu）封装 `su` 调用；Shizuku 作为无 root 的 ADB 级替代。

**方案**
1. **两个能力分开（2026-11-16 拍板）**，都注册在 `CapabilityHost`（kind 分别 `root` / `shell`）：
   - `root.exec {command}`：只在 `hasRoot()` 为真时出现/可用，走 `DeviceShell` 的 ROOT 身份；
     root 不可用时**如实返回** `{ok:false, reason:"root_unavailable"}`，**不降级到 Shizuku/App**；
   - `shell.exec {command}`：走 Shizuku（可用时）否则 App `sh`，同样返回
     `{exitCode, stdout, stderr, identity}`；
   - 另加只读的 `shell.status`：返回 `{root: bool, shizuku: bool, shizukuPermission: bool, default: "..."}`，
     给插件页/诊断页用。
2. **su 兼容与探测**：抽 `RootProbe` 依次尝试 `su -c id` / `su 0 id` / `su -0 -c id`，
   记录哪种成功；超时/授权弹窗（Magisk 首次会弹）要等待并给「正在等待 root 授权」状态；
   缓存结果，设置页可「重新检测」。
3. **可见性**：设置 →「权限与能力」增加「Shell 身份」行：`root / Shizuku / App` 当前值与原因；
   终端/虚拟屏启动失败时提示需要哪种身份。
